# 字幕实时采集、增量处理与持久累加：整合审核稿

日期：2026-10-11（Asia/Shanghai）

状态：待用户审核；本文不是已完成修改或性能达标报告。

## 1. 目标与已确认需求

让浏览器扩展在字幕文字可读取后及时采集和显示命中词库的单词，减少重复计算，并保留同一视频已经收集的内容。

用户已经确认的规则：

- 同一视频的新字幕只补充已有单词记录，不因字幕换句而删除旧词。
- 同一视频关闭后再次打开，保留之前收集的单词并继续累加。

本次此前讨论过、现统一提交审核的优化：

1. 弹窗打开期间自动更新新结果。
2. 新字幕采用增量发送、增量匹配，取消反复处理全部累计字幕。
3. 实时显示与合并保存分开，并能够在后台重启后恢复。
4. 修复字幕容器连接、重建及原生字幕兜底。
5. “重新抓取”按实际连接、等待、结果和失败状态更新界面。
6. 添加本地性能计时与针对上述行为的验证。

以下实现选择是建议，随本文一起接受审核，不表示用户已经逐项批准。

## 2. 当前证据与预期边界

当前 `content.js` 在每次字幕改变时发送全部累计字幕；`background.js` 从头建立单词表，并写入同一视频键；`popup.js` 打开时再次提交累计字幕，之后没有自动更新结果的订阅。

当前主通道已经采用 MutationObserver。连接正常后，它随字幕变化触发采集；其主要问题不是固定等待才分词，而是弹窗更新、重复处理、连接恢复及兜底可靠性。

本次用现有后台代码和实际三份词库，在 Node v24.15.0 / VM 中处理合成字幕的中位数：

| 测量项 | 中位耗时 |
| --- | --- |
| 单句分词、词形还原和词库匹配 | 约 0.04 ms |
| 处理累计 100 句 | 约 6.3 ms |
| 处理累计 1,000 句 | 约 60.5 ms |
| 处理累计 3,000 句 | 约 179.4 ms |

这些结果使用立即完成的模拟存储，不包含真实浏览器消息、持久化和 DOM 渲染；合成字幕也不能代表所有真实视频。它们不能当作真实端到端延迟或达标证明。

增量处理预计将累计 1,000 句的主要分词工作从约 500,500 句次降至约 1,000 句次，另加首次恢复、确有缺口的补发和一次性完整字幕导入。这不是整体速度提升 500 倍的承诺，排序、序列化、保存和渲染仍有成本。

“实时”的计时起点是页面英文字幕文字已经可读取。视频平台生成字幕、翻译扩展生成或显示字幕的上游延迟仍会存在。

## 3. 单词累加和持久保留

### 3.1 同一视频的合并规则

- 新词追加到该视频已有记录，不用本批字幕的结果替换全部旧词。
- 同一词再次出现，只补充出现时间点，不重复创建词卡。
- 建议沿用现有按小写字幕词形去重的规则。例如 `develop` 和 `developing` 仍可分别展示，并保留各自原型；本轮不改成按原型合并词卡。
- 建议保留每词最多 10 个不同时间点的现有规则。对已采到的时间点去重，按播放时间排序，展示前 10 个；这不等同于准确统计全部出现次数。
- 相同字幕在不同播放位置出现，可以补充新的时间点；不能继续用“整句文字只记录一次”作为所有出现位置的去重规则。
- 字幕修订、重发和重复观看不会删除已经收集的词。时间点是否新增按采集到的播放位置去重；没有精确字幕起点的 DOM 通道不能承诺跨次观看完全精确的出现次数。

### 3.2 哪些操作保留记录

| 操作 | 结果 |
| --- | --- |
| 出现下一句字幕 | 保留旧词，合并新增词和时间点 |
| 暂停、继续、快进、回看 | 保留旧词，继续合并有效采集结果 |
| 关闭、重新打开弹窗 | 恢复当前视频最新记录 |
| 刷新视频页面 | 恢复同一视频已保存记录，再继续采集 |
| 关闭视频，再打开同一视频 | 恢复已保存记录，再继续采集 |
| 点击“重新抓取” | 重连采集通道并补充记录，不清空历史词 |
| 切换到另一视频 | 展示和更新另一视频独立记录 |

保留以扩展本地存储仍然存在为前提。浏览器重启后恢复已持久化数据；不承诺恢复浏览器进程突然退出前尚未保存的内容。不新增自动清空规则，本轮也不新增清空视频记录按钮。

### 3.3 视频身份和旧记录

- 沿用已知平台的稳定视频 ID。YouTube 已有 `video_<videoId>` 记录保持可读取。
- 同一网站上多个视频不能仅因路径相同而自动混入一份记录。优先采用平台稳定 ID，媒体来源变化时重新判断当前视频身份。
- 建议对无法可靠判断身份的页面明确显示“无法确认当前视频”，继续提供当前页面的采集和累加，但不盲目合并历史记录。
- 此时为本次页面的媒体连接生成独立记录标识，采集结果仍写入本地历史，标题或状态标注身份未确认。关闭、刷新后已保存内容保留，可从历史查看；新页面不会自动绑定这份记录，因此同一视频可能留下多份独立记录。本轮不新增手动合并工具。
- 同页面检测到媒体来源变化时开始另一份独立记录，避免沿用旧会话积累到另一视频。如果连媒体切换也无法辨别，则暂停合并并显示无法确认状态，不能保证该页面可靠支持。
- 自动恢复并接续同一份记录的承诺只适用于能够可靠识别为同一视频的页面。上述身份未确认处理方式是待用户审核的建议，并非用户已批准的恢复例外。
- 非 YouTube 的旧“域名加路径哈希”记录保留在历史中。只有身份可核实时才绑定和合并，不批量删除，也不凭路径强行归属。
- 签名媒体 URL、同路径换视频等无法通用判断的情况，需要逐站验证；本轮不承诺所有视频站点的身份自动识别。

## 4. 增量采集与后台处理

### 4.1 页面只发送新增或修订的字幕

- 正常播放发送新增字幕事件，不在每次换句时构造、发送整段累计字幕。
- 消息包含视频身份、页面采集会话、事件标识、播放位置及字幕文本；具体字段命名留给实施。
- 区分页面连接会话和视频持久记录。刷新或“重新抓取”产生新的连接会话，不创建空记录覆盖同一视频的旧词。
- 在页面侧合并极短时间内的 DOM 变化，建议先以 50 ms 的短窗口处理逐段文字修订；必须设置最长等待，不能持续等到字幕完全停止变化才发出。
- 保留一次性完整字幕批量输入，用于现有原生字幕轨导入及确有必要的恢复；不要求大字幕轨逐句发送大量消息。
- 整轨导入维持现有可能一次收集完整视频词汇的行为，并在来源或状态中说明。它与随播放增量采集不同，其首次批量处理不纳入单句 300 ms 目标。

### 4.2 后台合并与去重

- 按视频维护已有单词索引，首次使用从本地记录恢复，之后只匹配新增或修订输入。
- 同一视频的更新串行合并；不同页面会话对同一视频的有效数据合并保存。页面会话用于识别过期界面更新，不用来丢弃另一页面采到的有效历史。
- 匹配合并队列与持久化队列分开：等待合并保存窗口或持久化确认不能阻塞下一批字幕的匹配和即时通知，否则会重新引入人为显示延迟。
- 重发消息具有可识别事件标识，避免同一已确认输入重复改变结果。
- 标准字幕轨采用其字幕起点；DOM 通道使用捕获时可获得的播放位置，继续承认它可能是近似值。
- 不同来源同时返回时统一进入同一合并流程，旧词始终保留。以单词及规范化播放时间点去重；来源起点存在偏差时不假称能完全合并同一次出现。
- 为视频记录或消息设置单调更新版本，防止旧响应晚到后覆盖更新的界面状态。
- 打开弹窗直接查询记录，取消再次发送全部累计字幕做匹配。
- “重新抓取”重新连接并检查来源；已经确认处理过的输入无需从头分词，确有修订或新输入才处理。

## 5. 实时界面与合并保存

### 5.1 弹窗更新

- 打开弹窗时主动查询当前页面身份及状态，再读取该视频最新记录。
- 后台合并完成后通知弹窗更新，不以持久化完成为前提。
- 无旧记录的空列表也能在第一批数据到达后自动显示词卡。
- 使用存储变化事件辅助恢复和同步。最终显示使用同一套词库标签和基础词过滤逻辑，不能直接把未过滤的存储记录显示出来。
- 自动更新绑定当前视频及更新版本；查看历史、查询详情或输入搜索时，保留当前操作上下文，不被其他视频的新消息切走。
- 新词卡和时间点更新尽量只更新受影响部分，避免每来一句字幕就重建全部卡片、重绑全部事件或重置滚动位置。
- 建议界面合并更新等待不超过 100 ms；数值需要真实浏览器验证和调整。
- 找不到当前视频记录时显示其等待状态，不能把上一视频记录冒充当前视频。

### 5.2 保存、确认和恢复

- 建议同一视频合并保存窗口为 500 ms，连续输入时最长约 1,000 ms 发起一次写入。该数值是调参起点，不是浏览器存储完成时间保证。
- 界面可显示尚未保存的最新合并结果；后台的最新记录查询也必须包含这些结果，不能在弹窗重开时只返回过期存储值。
- 页面保留未收到持久化确认的输入；仅在实际保存成功后确认对应版本。后台重新启动或连接恢复时，页面补发尚未确认的数据。
- 持久化写入按视频串行；保存进行期间出现的新输入进入下一次写入，避免旧写入晚完成后覆盖新结果。
- 复用现有本地存储，不把完整字幕长期作为新的持久化数据存入。页面只保留当前连接所需的缓存和未确认输入，并在确认后释放。
- 保存失败时保留待确认输入并显示保存失败状态；自动重试应有次数和内存边界。达到边界时明确暂停接收新输入并显示失败，已有待确认输入和旧记录保留，不悄悄删除旧记录或无限堆积；边界数值交给实施者根据输入量及测试确定。
- 只承诺在页面仍存在、仍保存待确认数据时补发未保存内容。页面与浏览器同时被突然关闭的最后一小段未保存内容属于明确恢复边界。

## 6. 字幕来源连接和兜底

### 6.1 沉浸式翻译通道

- 保留现有英文原文读取方式，不修改第三方字幕 DOM。
- 区分宿主已出现和 Shadow DOM 已准备好，避免观察到宿主就误判字幕连接完成。
- 容器被替换、字幕关闭后重开、页面导航或视频切换时，重新绑定有效字幕根。
- 用 DOM 变化发现相关容器，并在活跃视频上做低频连接检查。建议从 500 ms 检查间隔起步；不在所有无视频页面上永久高频扫描。
- 字幕晚于 60 秒出现时仍能重新连接，取消现有一次搜索超时后永久放弃的行为。
- 对无法读取的 closed Shadow DOM 显示来源不可用；回退读取宿主不能冒充已读到内部字幕。

### 6.2 标准原生字幕与 YouTube 兜底

- 页面提供可读取的英文 `video.textTracks` 时，优先采用 `cuechange` / 有效字幕事件；不能假设所有网站都暴露标准字幕轨。
- 沉浸式翻译英文原文通道继续可用；YouTube 整轨路径作为专用兜底。来源接管不能删除其他来源已收集的词。
- 修复 YouTube 直接从隔离内容脚本读取网页变量的问题。建议新增只匹配 YouTube 页面的、打包在扩展内的 MAIN world 桥接脚本；主要内容脚本仍保留隔离环境。
- 桥接仅传递字幕获取必要数据，校验消息来源及结构；不把远程返回内容当作可执行脚本。
- 如果采用该建议，需要调整 `manifest.json` 注册入口及对应 CI、发布打包清单，不扩大现有站点权限范围。浏览器最低版本支持情况在实施时核验并写入使用说明。
- 优先根据来源就绪事件连接，计时器只用于有界重试和失败判定；取消依赖固定 3 秒等待作为唯一启动条件。
- YouTube 播放器或字幕接口变化仍需真实页面验收。不能因桥接能取到一个变量就宣称原生字幕抓取已成功。
- 本轮不扩展为所有 iframe 视频和所有视频网站的通用抓取器。

## 7. “重新抓取”及可见状态

- “重新抓取”保留当前视频的词和时间点，只重连来源并合并后续数据。
- 去掉弹窗固定等待 1.5 秒后刷新；按采集状态及实际结果更新。
- 建议显示简短状态：正在连接、等待字幕、正在收集、暂无可读字幕、连接失败、保存失败。
- 区分“字幕已采到但没有新命中词”和“没有读到字幕”。词数未增加不自动显示为抓取失败。
- 明确没有字幕轨、通道不可读取、字幕请求失败和扩展脚本未连接等情况；诊断细节留在现有调试区域。
- 切换视频后忽略上一视频的晚到界面通知，但允许其有效数据完成自己的保存。

## 8. 保留现有行为与本轮范围

保留三份本地词库、单选词库显示、全部命中类别、基础词过滤、词形还原、已斩词、历史及本地优先在线补充查词。切换所选词库只改变显示，不重新处理全部字幕，不删除其他词库命中的采集数据。

建议修改范围：

| 文件或区域 | 预期改动 |
| --- | --- |
| `content.js` | 增量采集、待确认输入、视频身份和连接恢复、采集状态 |
| `background.js` | 持久记录合并、去重、每视频更新顺序、实时通知、合并保存及恢复 |
| `popup.js` | 当前视频绑定、订阅新结果、局部更新、保留界面上下文、重新抓取状态 |
| `popup.html` | 若现有区域不足，补充简短状态展示 |
| `manifest.json` / YouTube 桥接脚本 | 注册仅 YouTube 使用的页面脚本入口 |
| `README.md` / `docs/使用说明.md` / 隐私文案 | 说明累加、恢复、来源、限制及实际网络请求 |
| CI、发布打包清单、验证脚本 | 纳入新脚本和有意义的行为校验 |

`PROJECT_CONTEXT.md` 是已有未跟踪文件，本次审核稿不覆盖它。词库数据、许可和熟悉词记录不重建、不清空；不引入新框架、第三方运行依赖、OCR、语音识别、云端字幕上传或通用全站适配。

## 9. 性能目标与验收

### 9.1 本地计时

记录字幕可读取或捕获、后台收到输入、匹配合并完成、保存完成、词卡更新的阶段耗时，并汇总中位数和 P95。计时使用各上下文可对齐的时间基准；不要直接相减不同上下文的 `performance.now()`。

跨上下文测量可以使用 `performance.timeOrigin + performance.now()`；浏览器时间精度限制需要在结果中说明。用于真实画面起点的人工或浏览器性能面板检查，与从回调开始计时的结果分别标注，不能把捕获后的计时冒充完整字幕呈现延迟。

计时数据留在本地，不增加外部遥测。常规状态不展示实现细节；调试区域提供必要结果。

### 9.2 目标值

- 前台页面、弹窗持续打开、词库已加载、正常单句增量采集时，从英文字幕可读取到词卡更新，目标 P95 不超过 300 ms。
- 首次冷启动、首次恢复大记录、一次性整轨导入、后台页面降频、网络字幕请求等情况单独报告，不能混入或隐去后宣称所有路径都达到 300 ms。
- 连续播放 30～60 分钟后，新增单句的分词和匹配耗时不因累计句数明显增长。完整记录的保存和显示开销可能随词数增加，必须分别测量。
- 目标达不到时报告实测值及瓶颈，不以合成数据结果替代验收。

### 9.3 必须验证的行为

| 场景 | 通过条件 |
| --- | --- |
| 空记录播放首句及后续字幕 | 自动显示新词，旧词仍在 |
| 重复词、同句不同位置、输入重发 | 不重复词卡；补充不同时间点；同一已确认输入不重复处理 |
| 刷新、关闭重开同一视频 | 恢复已保存词并继续合并 |
| “重新抓取” | 不清空记录；状态及词表按实际结果更新 |
| 快速切视频、晚到消息 | 两个视频不串词，旧响应不覆盖当前界面 |
| 两个标签页采集同一视频 | 有效结果合并，没有相互覆盖 |
| 无法可靠确认视频身份 | 当前连接独立累加；已保存结果留在历史；重开不盲目自动绑定；能检测的媒体切换另开记录 |
| 字幕容器延迟出现、替换、开关字幕 | 在支持的页面自动恢复连接 |
| 弹窗持续打开、搜索、滚动、详情、历史 | 新结果自动更新，用户操作不被重置或切走 |
| 后台停止后恢复、保存失败 | 页面尚存的未确认输入可补发；失败明确显示；旧记录保留 |
| 三份词库、基础词过滤、已斩词、旧记录 | 展示规则及既有数据保持兼容 |
| 标准字幕轨与 YouTube 原生兜底 | 在真实页面验证有效字幕文本及时间点，不只验证脚本语法 |
| 长视频及真实端到端计时 | 报告浏览器、页面来源、视频长度、输入量及 P95 |

静态检查和 Mock 测试可先验证合并、重发、竞争写入、恢复与展示过滤。真实 Chrome / Edge 页面、实际字幕来源及网络兜底需要单独验收；未执行的场景必须标为未验证。

## 10. 建议实施顺序和交付

1. 完成视频记录合并、持久恢复、更新顺序、弹窗自动更新及“重新抓取”保留规则。先让行为正确，并保持现有来源入口可用。
2. 将正常采集改成增量消息，再拆分实时显示与合并保存，补齐确认和重发机制。
3. 修复容器连接恢复，接入可用标准字幕轨，完成 YouTube 桥接和原生兜底验证。
4. 做本地阶段计时、回归检查和真实浏览器验收，更新使用及隐私说明。

这是完整方案的实施次序，不表示只批准或只交付第一批。若某一来源无法在真实环境完成验收，应单独记录原因和已完成范围。

交付包含：源码变更、可运行的验证、实际测试结果、更新后的说明，以及明确标注的未验证或不支持场景。现有无构建开发方式保留；源文件更新后需重新加载扩展并刷新视频页面。

## 11. 用户审核时的主要取舍

除已确认的“同一视频累加并在重开后保留”外，建议一并审核：

- 按现有字幕词形去重，保留每词最多 10 个时间点；不是全量出现次数统计。
- “重新抓取”只重连和补充，不承担清空功能。
- 保留一次性整轨导入，因此该通道可能提前收集未播放部分的词。
- 对身份不可靠的视频继续独立采集并保存历史，不盲目自动接续；重开可能产生多份记录。这一恢复例外需要审核，完整自动接续仍需逐站支持。
- 采用仅 YouTube 使用的 MAIN world 桥接入口，并在真实页面验证其兼容性。
- 采用短窗口合并界面与保存；后台重启可补发以页面仍存活为条件，突然同时关闭前未保存内容不作完整恢复承诺。
- P95 ≤ 300 ms 是限定场景下的验收目标，实测后才能判断是否达标。

本审核稿不代表程序代码已修改。用户批准完整范围后，才进入实施计划和编码。
